# モジュール境界・依存規則（Boundaries）

* Version: 0.3.0（Proposed / ドラフト）
* Date: 2026-04-01
* Last amended: 2026-09-06
* 上位規範: constitution.md（開発憲章「アーキテクチャの完全性」）／ standards/architecture-standards.md

本書は、レイヤ構成・モジュール境界・依存規則の正本（SSoT）です。

> **なぜこの文書が重要か**: 統治・規範レイヤ（constitution.md 等）が「誰が承認するか」を定めるのに対し、
> 本書は「どう分ければレビュアが読む必要のある範囲を狭められるか」を定めます（局所性。憲章「3. 基本原則」
> 検証手段の選択と対をなす、レビューコストそのものを下げる側の設計）。境界が曖昧なままだと、1行の変更が
> リポジトリ全体に波及しうるかを毎回人間が判断することになり、機械検証（`scripts/checks/arch-boundaries.sh`）
> も効かない。**採用時に必ず「レイヤ構成」を実プロジェクトの構成へ置き換えてください**（下記は未確定のままの
> プレースホルダ例であり、このまま使うものではありません）。

---

## レイヤ構成（未確定・採用組織が確定する。以下は記入例）

```text
例:
  presentation（UI・API ハンドラ）
    → application（ユースケース・オーケストレーション）
      → domain（ビジネスルール。外部依存を持たない）
      ← infrastructure（DB・外部API・ファイルシステム等のアダプタ）

依存は内側（domain）へ向き、domain は外側（infrastructure・application・presentation）に依存しない。
domain が外部ライブラリに直接依存する場合は、infrastructure 側にアダプタ（ポート/アダプタパターン等）を置く。
```

採用組織は、上記を実際のレイヤ名・依存方向へ書き換えてください。モノレポでパッケージ／ディレクトリ単位の
境界を持つ場合は、パッケージ名と許可される依存方向の対応表として書き直してもかまいません。

## デプロイ単位

[architecture/principles.md](principles.md) 原則6・7 が定める三軸（縦・横・物理論理）を、本プロジェクトの
構成へ対応づけます。上の「レイヤ構成」は**横軸**（各縦の内部構造）の記入例であり、本節はそこに**縦軸**
（モジュール境界）と**物理／論理軸**（デプロイ単位）を重ねます。3軸は独立であり、横軸の記入例をそのまま
縦軸の分割単位と読み替えてはなりません。

### 三軸対応表（未確定・採用組織が確定する。以下は記入例）

| 縦（モジュール／機能境界） | 横（レイヤ。上の「レイヤ構成」を各縦に適用） | 物理／論理（デプロイ単位） |
| --- | --- | --- |
| 例: 注文管理 | presentation → application → domain ← infrastructure | 論理（単一デプロイ単位内のモジュール） |
| 例: 顧客管理 | 同上 | 論理（同上） |
| 例: 決済連携（外部ベンダとの契約により分離済み） | 同上 | 物理（別デプロイ単位。理由は ADR に記載） |

採用組織は、上表を実際のモジュール名・デプロイ単位へ書き換えてください。**既定はすべてのモジュールが
単一のデプロイ単位（モジュラーモノリス）に属する論理分割**です。ある行を物理分割にする場合、
[architecture/principles.md](principles.md) 原則7が定める「現在すでに成立している理由」（確定済みの
ベンダ分割契約・セキュリティゾーンの相違・ランタイム特性の相違・組織の既存プラットフォーム標準の
いずれか）を ADR に記載しなければなりません（MUST。判断根拠は
[ADR-0009](../adr/adr-0009-default-deployment-unit-policy.md)）。将来的な拡張見込みのみを理由に
物理分割してはなりません（MUST NOT）。

### 既定（モジュラーモノリス）採用時の追加義務

既定どおり単一デプロイ単位（モジュラーモノリス）を採用する場合、上の「レイヤ構成」を**実プロジェクトの
構成へ実体化した上で**、循環依存の機械検証ゲート（`ARCH_BOUNDARY_CMD`。次節「依存規則」参照）を
配線しなければなりません（MUST。standards/architecture-standards.md「2.」）。理由: 機械強制のない
論理分割は時間の経過とともに密結合へ退化し、本書が既定として温存しようとしている選択肢——後から
物理分割へ切り出せる余地——そのものを失うためです。

## 依存規則

- 循環依存を導入してはなりません（MUST NOT）。機械検証の休眠/活性化ゲートは `scripts/checks/arch-boundaries.sh`
  として既に配線済みです（sast.sh と同一パターン。対象スタックを検出すると活性化し、`ARCH_BOUNDARY_CMD` 環境変数
  または `scripts/dev/arch-boundary-tool.sh` で実ツール（import-linter / dependency-cruiser / ArchUnit /
  go-arch-lint 等、スタックに応じて選定）を配線するまでは「未配線」として正直に警告します。強制台帳の当該行を参照）。
- 境界を越える通信は公開契約（API・イベント）を通じて行うべきです（SHOULD）。
