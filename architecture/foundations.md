# foundations.md — 稼働後に変更困難な決定（Foundational Decisions）

* Version: 0.1.0（Proposed / ドラフト）
* Date: 2026-09-06
* 上位規範: [constitution.md](../constitution.md)「アーキテクチャの完全性」／[architecture/roadmaps/uncertainty-profile.md](roadmaps/uncertainty-profile.md)
* 変更クラス: **B**（アーキテクチャ。原則 ADR 化）

本書は、**本番稼働を開始した後に変更することが著しく困難、または実務上不能な基盤決定**の一覧を
規範化する正本（SSoT）です。[uncertainty-profile.md](roadmaps/uncertainty-profile.md) が示す
「両振れの不確実性」のうち、規模や機能範囲が変わっても後から変更できる決定とは異なり、本書が扱う決定は
**規模の縮小・拡大のいずれのシナリオでも、先に確定しておかなければ後から払うコストが不釣り合いに高い**
という性質を持ちます。

> **domain-models/ との違い**: [architecture/domain-models/](domain-models/) は機能横断の**概念モデル**
> （集約・エンティティ・不変条件）を扱います。本書はモデルの内容ではなく、**モデルの土台となる、後から
> 変更すると既存データ・既存契約・既存連携のすべてに波及する決定**を扱います。両者は役割が異なり、
> 一方が他方を複写しません（SSoT）。domain-models/ の集約定義は、本書が確定した ID 体系・テナント軸等を
> 前提として設計されます。

---

## 1. 本書の使い方

以下の各項目は、**未確定のまま実装に着手してはなりません（MUST NOT）**。個別プロジェクトは、
着手前に該当項目を ADR で確定し、本書の「決定状況」欄（採用組織が追記）に確定済み ADR への参照を
記入します。

具体的な採番方式・データ型・許容値は、ドメイン・技術スタックに依存するため、本書では**記入例**に
とどめます（本テンプレートは公開・スタック中立。憲章「10.1.3 推測の禁止」と同じ趣旨をアーキテクチャ層へ
適用）。**採用組織が ADR で確定してください。**

## 2. 決定項目一覧

### 2.1 ID 体系

* 採番方式（連番／UUID／ULID／その他）を確定する。
* **内部 ID と公開 ID を分離するか**を確定する。分離する場合、公開 ID の推測困難性・失効/再発行の
  取り扱いを定める。
* ID の名前空間（グローバル一意か、テナント／集約単位で一意か）を確定する。
* 未確定のまま永続化スキーマを実装してはなりません（MUST NOT）。ID 体系の変更は、既存データの
  全件移行を要するため、本番稼働後は実務上最もコストの高い変更のひとつです。

### 2.2 テナント／組織軸

* データモデルにマルチテナント軸（テナントID・組織ID等）を持たせるかどうかを確定する。
* 持たせる場合、テナント分離の粒度（行レベル／スキーマレベル／データベースレベル）を確定する。
* 「今はシングルテナントだが将来マルチテナント化するかもしれない」という将来形の理由だけで
  軸の追加を先送りしてはなりません（MUST NOT）。テナント軸は、後から全テーブル・全クエリに
  遡及的に追加することが著しく困難な決定であるため、シングルテナント運用を選ぶ場合も
  「シングルテナントである」ことを明示的な決定として記録します。

### 2.3 履歴・論理削除・監査ログ

* 更新履歴を保持するか（イベントソーシング／履歴テーブル／変更なし）を確定する。
* 削除を論理削除（ソフトデリート）とするか物理削除とするかを、エンティティ種別ごとに確定する。
* 監査ログ（誰が・いつ・何を変更したか）の保持要否・保持期間を確定する（憲章「監査証跡」）。
* 未確定のまま物理削除を既定として実装してはなりません（MUST NOT）。物理削除を後から論理削除へ
  切り替えても、切り替え以前に失われたデータは復元できません。

### 2.4 日時のタイムゾーン表現

* 永続化層・API境界における日時の表現（UTC 固定か、オフセット付きか、ローカルタイムゾーンを
  別途保持するか）を確定する（api-standards.md「3.」RFC 3339 準拠と整合させる）。
* 未確定のまま日時カラムを実装してはなりません（MUST NOT）。表現方式の変更は、既存の全レコードの
  意味を変えるため、後から機械的に「変換」できても「どちらの意図だったか」を復元できないことがある。

### 2.5 通貨

* 金額を扱う場合、通貨の表現（単一通貨固定か多通貨対応か）、金額の精度・丸め規則、
  通貨コードの体系（ISO 4217 等）を確定する。
* 未確定のまま金額カラムを実装してはなりません（MUST NOT）。単一通貨前提で実装した金額データは、
  多通貨対応への移行時に「どの通貨だったか」が記録されておらず復元不能になりうる。

### 2.6 多言語（i18n / l10n）

* コンテンツ・マスタデータの多言語対応要否、対応する場合の翻訳データの持ち方
  （カラム分割／関連テーブル／外部i18n基盤）を確定する。
* 未確定のまま単一言語決め打ちでマスタデータを実装してはなりません（MUST NOT）。後から多言語化する
  場合、どの言語のテキストがどの項目に対応するかの遡及的な仕分けが必要になる。

### 2.7 コード値マスタの所有主体

* コード値（ステータス・区分・種別等の列挙値）マスタを、どのモジュール／チームが所有し、
  追加・変更の権限を持つかを確定する。
* 未確定のまま複数モジュールがコード値を独自に重複定義してはなりません（MUST NOT）。所有主体が
  後から定まっても、既に重複定義されたコード値の統合は、参照している全箇所の調査を要する。
